# 커넥션 풀 한계 기준

## 출처

- 출처 id: `prisma-connection-pool`
- URL: https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/connection-pool
- 소유자: Prisma Data
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: 커넥션 풀 크기·타임아웃 설정과 서버리스 환경 판정에만 사용한다.
- 검토 스냅샷: `prisma-connection-pool` 구조 `b2ecb45fbeed` 본문 `af2d239912ca`

## 이 문서가 해당 역할에 도움이 되는 이유

느린 쿼리 문제가 커넥션 고갈로 번지면 증상이 전혀 다르게 나타난다. 풀 크기 기본값과
타임아웃이 버전·드라이버마다 다르므로, 설정을 확인하지 않고 내리는 성능 판정은 빗나간다.
공식 문서가 기본값과 제약을 규정한다.

## 프로젝트에 적용할 기준

- 풀 크기는 데이터베이스가 감당할 수 있는 한계를 넘을 수 없다. 애플리케이션 인스턴스 수를 곱해 계산한다.
- 서버리스에서는 함수 인스턴스마다 자체 풀을 갖는다. 외부 커넥션 풀러 도입을 검토한다.
- 풀 크기와 타임아웃 기본값은 Prisma 버전과 드라이버에 따라 다르다. 성능을 판정하기 전에 실제 설정을 확인한다.
- 버전을 올릴 때 이전 동작을 유지하려면 타임아웃을 명시적으로 설정한다.
- 커넥션 대기 시간이 문제라면 쿼리 개선과 풀 크기 조정 중 무엇이 원인인지 먼저 가른다.

## 주의할 점

- 풀을 키우는 것이 항상 해결책은 아니다. 데이터베이스 쪽 한계를 넘기면 더 나빠진다.
- 긴 트랜잭션은 커넥션을 오래 붙잡아 풀 고갈의 직접 원인이 된다. 트랜잭션 문서와 함께 본다.
- 버전 간 기본값 차이가 크므로 문서의 수치를 그대로 인용하기 전에 프로젝트 버전을 확인한다.

## 에이전트가 사용할 때의 체크리스트

- 풀 크기가 인스턴스 수를 곱해도 데이터베이스 한계 안에 있는가?
- 서버리스라면 외부 풀러를 검토했는가?
- 성능 판정 전에 실제 풀 설정과 Prisma 버전을 확인했는가?
- 커넥션 고갈이 긴 트랜잭션 때문은 아닌가?
