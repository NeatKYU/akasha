# 관계 로딩과 과다 조회 기준

## 출처

- 출처 id: `prisma-relation-queries`
- URL: https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries
- 소유자: Prisma Data
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: 관계 로딩 전략과 필드 선택 판정에만 사용한다.
- 검토 스냅샷: `prisma-relation-queries` 구조 `24ef0cd5b007` 본문 `189e58a7d85f`

## 이 문서가 해당 역할에 도움이 되는 이유

관계를 어떻게 불러오느냐가 쿼리 수와 전송량을 동시에 좌우한다. `include`를 넓게 열면
쿼리 수는 줄어도 전송량이 폭증하고, fluent API를 반복하면 쿼리가 늘어난다. 공식 문서가
각 방식의 동작을 규정하므로 선택의 대가를 근거 있게 지적할 수 있다.

## 프로젝트에 적용할 기준

- 필요한 필드만 명시적으로 `select`한다. `include`로 모델 전체를 끌어오지 않는다.
- `select`와 `include`를 같은 레벨에 함께 쓰지 않는다. 중첩이 필요하면 `include` 안에 `select`를 둔다.
- 관계 필터·정렬·페이지네이션은 중첩 옵션으로 표현해 애플리케이션에서 거르지 않는다.
- fluent API 체이닝은 쿼리를 여러 번 만든다. 단건 조회 뒤 관계를 따라가는 경우에만 쓴다.
- 목록 결과에 fluent API를 이어 붙이지 않는다. 관계 필터를 쓴 `findMany` 한 번으로 표현한다.
- join 전략과 query 전략 중 무엇이 유리한지는 케이스마다 다르다. 바꾸려면 프로파일 근거를 남긴다.

## 주의할 점

- `createMany`는 관계 필드에 접근할 수 없다. 관련 레코드를 함께 만들 수 없다.
- join 전략은 데이터베이스에서 JSON 집계를 수행한다. 애플리케이션 부하는 줄지만 DB 부하는 늘 수 있다.
- 관계 로딩 전략 선택 기능은 프리뷰 플래그와 데이터베이스 종류에 따라 가용 여부가 다르다.

## 에이전트가 사용할 때의 체크리스트

- 필요한 필드만 선택하고 있는가, 모델 전체를 끌어오는가?
- 목록 결과에 fluent API를 이어 붙여 쿼리를 늘리고 있지 않은가?
- 관계 필터를 애플리케이션이 아니라 쿼리에서 처리하는가?
- 로딩 전략을 바꿨다면 프로파일 근거가 있는가?
