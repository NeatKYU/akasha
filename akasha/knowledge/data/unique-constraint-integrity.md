# 고유 제약과 데이터 계약 변경 기준

## 출처

- 출처 id: `postgres-unique-constraints`
- URL: https://www.postgresql.org/docs/current/ddl-constraints.html
- 소유자: PostgreSQL Global Development Group
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: UNIQUE 제약 추가·제거가 데이터 중복 허용 범위와 인덱스 계약에 미치는 영향 판정에만 사용한다.
- 검토 스냅샷: `postgres-unique-constraints` 구조 `bf86bbddbad2` 본문 `129f71d8532a`

## 이 문서가 해당 역할에 도움이 되는 이유

고유 제약은 단순한 schema 장식이 아니라 어떤 값의 중복을 데이터베이스가 거부하는지 정하는
계약이다. 제약을 제거하면 허용 가능한 행 집합이 바뀌므로, 도메인 cardinality와 migration
근거 없이 성능 변경으로만 다루면 데이터 무결성 변화를 놓칠 수 있다.

## 프로젝트에 적용할 기준

- 단일 컬럼 또는 컬럼 조합의 `UNIQUE` 제약은 해당 값 조합의 중복 행을 데이터베이스가 거부하게 한다.
- 고유 제약을 제거하면 이전에 거부되던 중복 값이 허용될 수 있다. 제거 자체를 무조건 위반으로
  단정하지 말고, 의도한 일대일·일대다 cardinality 계약과 일치하는지 확인한다.
- schema 정의에서 고유 제약이 추가·제거됐는데 대응 migration 산출물이 없으면 실제 데이터베이스에
  적용되는 변경인지 확인할 근거가 부족하다고 보고한다.
- 기존 데이터와 새 쓰기 경로가 변경된 중복 허용 범위를 감당하는지 검증 근거를 요구한다.
- PostgreSQL은 고유 제약을 만들 때 고유 B-tree 인덱스를 자동 생성한다. 제약 변경의 성능 효과는
  별도 실행 계획과 대표 데이터로 검증하고, 무결성 계약과 섞어 단정하지 않는다.

## 주의할 점

- nullable 컬럼의 중복 판정은 null 비교 방식에 따라 달라진다. null이 포함된 경우를 일반 값과 같게
  취급하지 않는다.
- 여러 컬럼의 고유 제약은 각 컬럼이 아니라 조합 전체의 유일성을 보장한다.
- 고유 제약 제거가 올바른 요구사항 변경일 수 있다. 요구사항·migration·기존 데이터 근거가 없다는
  사실과 제약 제거 자체의 확정 효과를 구분한다.
