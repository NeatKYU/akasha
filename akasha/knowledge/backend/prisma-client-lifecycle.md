## 출처

- URL: https://www.prisma.io/docs/orm/more/best-practices
- 소유자: Prisma Data
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: Prisma Client 인스턴스 관리, 페이지네이션, 마이그레이션 판정에만 사용한다.
- 검토 스냅샷: `prisma-best-practices` 구조 `0a2023e31502` 본문 `0fd663d9e6e0`

## 이 문서가 해당 역할에 도움이 되는 이유

커넥션 고갈은 쿼리 성능 문제로 위장해서 나타난다. 원인이 클라이언트 인스턴스를 여러 개
만든 것이면 쿼리를 아무리 고쳐도 해결되지 않는다. 공식 권고가 인스턴스 관리와 운영
마이그레이션을 규정하므로, 증상 뒤의 구조 문제를 지목할 수 있다.

## 프로젝트에 적용할 기준

- `PrismaClient` 인스턴스를 하나 만들어 애플리케이션 전체에서 재사용한다. 인스턴스마다 별도 커넥션 풀이 생긴다.
- 서버리스에서는 핸들러 함수 안이 아니라 밖에서 초기화해 warm invocation 간에 재사용되게 한다.
- 목록을 가져온 뒤 항목마다 쿼리하지 않는다. `include`나 `IN` 필터를 쓴 배치 조회로 바꾼다.
- `select`로 필요한 필드만 가져오거나 `omit`으로 민감 필드를 제외한다.
- 대용량 데이터는 오프셋이 아니라 커서 기반 페이지네이션을 쓴다. 인덱스로 시작 위치를 찾는다.
- raw 쿼리는 파라미터화하거나 태그드 템플릿을 쓴다. 사용자 입력을 문자열로 이어붙이지 않는다.
- 운영 마이그레이션은 `migrate deploy`만 쓴다. `migrate dev`나 `db push`를 운영에 쓰지 않는다.

## 주의할 점

- 개발 환경의 핫 리로드가 인스턴스를 반복 생성해 커넥션을 소진할 수 있다. 전역 보관 패턴을 확인한다.
- 커서 페이지네이션은 정렬 기준이 안정적인 인덱스 컬럼일 때 의미가 있다.
- 이 문서는 운영 권고를 다룬다. 풀 크기 수치와 타임아웃은 커넥션 풀 문서를 본다.

## 에이전트가 사용할 때의 체크리스트

- `PrismaClient` 인스턴스가 하나로 유지되는가?
- 서버리스에서 핸들러 안에서 인스턴스를 만들고 있지 않은가?
- 루프 안 쿼리를 배치로 바꿀 수 있는가?
- raw 쿼리에 사용자 입력이 문자열로 이어붙지 않는가?
- 운영 마이그레이션이 `migrate deploy`인가?
