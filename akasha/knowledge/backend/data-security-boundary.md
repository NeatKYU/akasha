## 이 문서가 해당 역할에 도움이 되는 이유

백엔드 에이전트는 서버 컴포넌트와 서버 액션을 단순한 렌더링 도구가 아니라 권한, 데이터 최소화, 비밀값 접근 경계가 걸린 서버 실행면으로 다뤄야 한다. 이 기준은 데이터를 어디서 읽고, 어떤 형태로 클라이언트에 넘기며, mutation에서 인증과 인가를 어디서 다시 확인할지 판단하는 데 도움을 준다.

특히 App Router 기반 프로젝트에서는 API Route, 서버 컴포넌트, 서버 액션, 클라이언트 컴포넌트가 한 코드베이스에 섞이기 쉽다. 역할별 책임을 명확히 나누지 않으면 안전한 서버 코드가 렌더 트리를 통해 클라이언트 props로 흘러갈 수 있다.

## 프로젝트에 적용할 기준

- 새 기능에서는 데이터 접근 계층을 먼저 설계하고, 데이터베이스 접근·권한 확인·반환 DTO 생성을 그 안에 모은다.
- 클라이언트 컴포넌트에 전달하는 값은 화면에 필요한 필드만 담은 DTO로 제한하고, ORM row나 도메인 객체 전체를 그대로 넘기지 않는다.
- 비밀값과 환경 변수 접근은 서버 전용 모듈로 가둔다. `NEXT_PUBLIC_` 접두사가 필요한 값인지 별도로 검토하고, 기본값처럼 공개하지 않는다.
- 서버 전용 데이터 접근 파일에는 `server-only` 같은 서버 전용 경계 장치를 사용해 실수로 클라이언트 번들에 섞이는 일을 막는다.
- Server Action은 직접 POST로 호출될 수 있다고 가정하고, 페이지 수준 로그인 확인과 별도로 액션 내부 또는 데이터 접근 계층에서 인증·인가·소유권을 다시 확인한다.
- mutation은 렌더링 중 부수 효과로 처리하지 않고, 서버 액션이나 명시적 서버 API에서 입력 검증, 권한 확인, 저장, 반환값 필터링을 한 흐름으로 묶는다.

## 주의할 점

- 서버 컴포넌트가 서버에서 실행된다는 사실만으로 반환 데이터가 안전해지는 것은 아니다. 클라이언트 컴포넌트 props로 넘어가는 순간 브라우저 노출을 전제로 검토해야 한다.
- 실험적 taint 계열 보호는 보조 장치로 보고, 기본 통제는 데이터 접근 계층의 필터링과 DTO 설계에 둔다.
- 기존 REST 또는 GraphQL API를 계속 쓰는 대형 프로젝트에서는 서버 컴포넌트가 API 보안 모델을 우회하지 않도록 토큰 전달, 감사, 권한 검사를 기존 경계와 맞춘다.
- 액션 ID 난독화나 프레임워크의 CSRF 완화에 기대어 권한 검사를 생략하지 않는다.
- 한 요청 안에서 캐시된 사용자 컨텍스트를 재사용하더라도, 리소스별 권한과 소유권 판단은 mutation 또는 조회 단위로 확인한다.

## 에이전트가 사용할 때의 체크리스트

- [ ] 데이터 읽기 경로가 HTTP API, 데이터 접근 계층, 컴포넌트 직접 접근 중 하나로 설명되는가?
- [ ] 서버에서 읽은 객체 전체가 클라이언트 컴포넌트 props로 전달되지 않는가?
- [ ] DTO가 화면에 필요한 최소 필드만 포함하고 민감 필드는 기본적으로 제외하는가?
- [ ] 데이터베이스 패키지와 환경 변수 접근이 서버 전용 모듈 바깥으로 새지 않는가?
- [ ] Server Action마다 인증, 인가, 리소스 소유권, 입력 검증, 반환값 필터링이 확인되는가?
- [ ] 변경 후 테스트나 코드 리뷰에서 클라이언트 번들·props·네트워크 응답에 민감 데이터가 없는지 확인했는가?
