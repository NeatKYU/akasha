## 이 문서가 해당 역할에 도움이 되는 이유

"이건 공용 컴포넌트로 만들자"는 제안은 근거 없이 나오면 시스템을 부풀린다. GOV.UK 디자인
시스템은 제안이 거쳐야 할 단계와 요구 근거를 규정하므로, 조사 없이 올라온 제안을 절차
미이행으로 지적할 수 있다.

## 프로젝트에 적용할 기준

- 제안 전에 기존 구현부터 조사한다. 정부·조직 안팎에 이미 있는 것을 문서화한다.
- 이미 진행 중인 논의가 있는지 확인해 중복 작업을 만들지 않는다.
- 실제 서비스 또는 현실적인 프로토타입에서 수행한 사용자 조사 근거를 제시한다.
- 일반 수용 기준과 해당 컴포넌트 고유 기준 양쪽으로 접근성을 시험한다.
- 제안 → 착수 협의 → 개발 중 정기 확인 → 검토 제출 → 보완 → 공개의 단계를 밟는다.

## 주의할 점

- 이 절차는 GOV.UK 디자인 시스템의 것이다. 프로젝트 규모와 팀 구조에 맞게 조정해야 한다.
- 문서에 명시적인 거절 사유 목록은 없다. 프로젝트가 자체 기준을 정해야 한다.
- 절차를 갖췄다는 사실이 컴포넌트가 필요하다는 근거는 아니다. 반복되는 수요가 먼저다.

## 에이전트가 사용할 때의 체크리스트

- 기존 구현 조사가 제안에 포함되어 있는가?
- 사용자 조사 근거가 실제 서비스나 현실적 프로토타입에서 나왔는가?
- 접근성 시험 계획이 있는가?
- 이미 있는 컴포넌트로 해결되지 않는 이유가 설명되어 있는가?
