## 이 문서가 해당 역할에 도움이 되는 이유

"입력을 검증하라"는 지시만으로는 판정이 불가능하다. 무엇을 허용 목록으로 잡을지, 구문 검증과
의미 검증을 어디서 나눌지, 검증이 무엇을 막지 **못하는지**가 규정되어야 한다. 이 기준은 그
세 가지를 모두 다루므로 검증이 있는 것처럼 보이지만 실제로는 없는 코드를 가려낼 수 있다.

## 프로젝트에 적용할 기준

- 허용 목록(allowlist)으로 검증한다. 위험한 문자·패턴을 막는 차단 목록은 보조 수단일 뿐 대체재가 아니다.
- 구문 검증(형식·길이·범위)과 의미 검증(업무 규칙)을 나눠서 수행한다. 시작일이 종료일보다 앞선다 같은 조건은 의미 검증이다.
- 검증은 서버 측에서, 데이터가 어떤 기능에 쓰이기 **전에** 수행한다. 클라이언트 검증은 UX용이다.
- 정규식은 입력 전체를 덮도록 앵커를 쓰고 최소·최대 길이를 정의한다.
- 파일 업로드는 확장자 허용 목록, 크기 제한, 무작위 이름 재지정, 서버가 정한 저장 경로, 내용 기반 검사를 함께 적용한다.
- 이메일은 구문 검증만으로 끝내지 않고 일회용 토큰이 담긴 확인 메일로 의미 검증을 한다.

## 주의할 점

- 입력 검증은 XSS나 SQL 인젝션의 **주된** 방어 수단이 아니다. 출력 인코딩과 컨텍스트에 맞는 이스케이프가 따로 필요하다.
- 차단 목록은 우회가 쉽고, 정상 입력(예: `O'Brian`)을 막는 부작용이 있다.
- 업로드 파일의 `Content-Type` 헤더를 신뢰하지 않는다. 감지된 실제 형식으로 판단한다.
- 일회용 이메일 차단은 사실상 불가능하다. 그 방향으로 노력을 쏟지 않는다.

## 에이전트가 사용할 때의 체크리스트

- 검증이 허용 목록 방식인가, 위험 패턴 차단 방식인가?
- 서버 측에서, 데이터가 사용되기 전에 검증하는가?
- 구문 검증만 있고 업무 규칙 검증이 빠져 있지 않은가?
- 정규식이 입력 전체를 덮고 길이 제한이 있는가?
- 파일 업로드에 확장자·크기·저장 경로·내용 검사가 함께 있는가?
- 출력 인코딩을 입력 검증으로 대신하고 있지 않은가?
