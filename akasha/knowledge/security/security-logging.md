# 보안 로깅 기준

## 출처

- 출처 id: `owasp-logging`
- URL: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html
- 소유자: OWASP
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: 무엇을 로그로 남기고 무엇을 남기지 않을지 판정에만 사용한다.
- 검토 스냅샷: `owasp-logging` 구조 `80243e155ed3` 본문 `d0aaabaee5ba`

## 이 문서가 해당 역할에 도움이 되는 이유

로그는 사고를 조사할 유일한 근거인데, 동시에 비밀값이 새는 가장 흔한 통로다. 무엇을 반드시
남기고 무엇을 절대 남기지 않아야 하는지가 규정되어야 "로그를 남겼다"와 "로그로 유출했다"를
가를 수 있다. OWASP 기준은 양쪽을 목록으로 규정한다.

## 프로젝트에 적용할 기준

- 인증 성공·실패, 인가 실패, 입력 검증 실패, 세션 처리 실패, 관리 작업, 민감 데이터 접근을 로그로 남긴다.
- 비밀번호·세션 식별자·토큰·암호화 키·결제 정보·개인식별정보·DB 접속 문자열을 그대로 남기지 않는다. 마스킹하거나 해시한다.
- 각 항목에 언제·어디서·누가·무엇을 남긴다 — 시각, 애플리케이션과 위치, 사용자와 출발지, 이벤트 종류와 결과.
- 다른 신뢰 구역에서 온 이벤트 데이터는 형식을 검증하고 개행·구분자를 제거해 로그 주입을 막는다.
- 내부 시스템·신뢰하는 제3자·모니터링에서 온 이벤트도 제외하지 않는다. 필요하면 분류 플래그로 구분한다.
- 로깅 실패가 애플리케이션 동작을 막거나 민감 정보를 노출하지 않게 한다.

## 주의할 점

- 로그 자체가 서비스 거부 경로가 될 수 있다. 공격자가 디스크를 채우지 못하게 설계한다.
- 로그 수준을 조정할 수 있어도 컴플라이언스가 요구하는 이벤트는 끌 수 없다.
- 사용자가 동의하지 않은 데이터를 법적 근거 없이 남기지 않는다.

## 에이전트가 사용할 때의 체크리스트

- 인증·인가 실패가 로그로 남는가?
- 비밀번호·토큰·세션 식별자가 평문으로 남지 않는가?
- 각 항목이 시각·주체·결과를 식별할 수 있는가?
- 외부 입력이 로그에 그대로 들어가 주입 경로가 되지 않는가?
- 로깅 실패가 요청 처리를 막지 않는가?
