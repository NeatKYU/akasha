# Prisma 쿼리 패턴과 N+1 진단 기준

## 출처

- 출처 id: `prisma-query-optimization`
- URL: https://www.prisma.io/docs/orm/prisma-client/queries/advanced/query-optimization-performance
- 소유자: Prisma Data
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다.
- 사용 메모: Prisma Client 쿼리 병목과 N+1 패턴을 진단할 때만 사용한다.
- 검토 스냅샷: `prisma-query-optimization` 구조 `85ce880f49ec` 본문 `778a52074355`

## 이 문서가 해당 역할에 도움이 되는 이유

데이터 에이전트는 데이터베이스에 도달하기 전 애플리케이션 쪽에서 만들어지는 쿼리 수와 관계 로딩
비용을 먼저 본다. Prisma 공식 문서는 반복 호출과 관계 로딩이 어떻게 병목이 되는지와 배치·명시적
relation loading으로 줄이는 기준을 제공한다.

## 프로젝트에 적용할 기준

- 성능 변경 PR은 영향을 받는 API, Prisma 호출, 예상 데이터 규모를 함께 적는다.
- `include`, 관계 필드 반복 접근, 루프 안의 쿼리 호출은 N+1 가능성으로 보고 배치 또는 명시적 relation loading을 검토한다.
- 대량 읽기·쓰기는 개별 호출 대신 배치로 처리하는 편이 일반적으로 유리하다.
- 쿼리 수 감소 주장은 Prisma query log나 호출 위치로 확인한다.
- ORM 레벨 개선이 데이터베이스 비용을 늘리지 않는지 실행 계획으로 교차 확인한다.

## 주의할 점

- ORM 레벨에서 호출 수가 줄어도 데이터베이스에서는 더 비싼 join이나 정렬이 생길 수 있다.
- `include`를 넓히면 전송량과 메모리가 함께 늘어난다. 필요한 필드만 선택했는지 확인한다.
- 트랜잭션 안에서 네트워크 호출이나 느린 쿼리를 실행하면 커넥션을 오래 붙잡는다.

## 에이전트가 사용할 때의 체크리스트

- 느린 사용자 흐름과 연결된 API 또는 서버 액션을 특정했는가?
- query log나 호출 위치로 반복 쿼리와 관계 로딩 패턴을 확인했는가?
- 필요한 필드만 선택하고 있는가?
- 쿼리 수 감소가 데이터베이스 비용 증가로 상쇄되지 않는지 확인했는가?
