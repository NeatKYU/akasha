# 사용자 스토리 분할 기준

## 출처

- 출처 id: `govuk-user-stories`
- URL: https://www.gov.uk/service-manual/agile-delivery/writing-user-stories
- 소유자: UK Government Digital Service
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다.
- 사용 메모: 제품 백로그 분할과 수용 조건 검토 기준으로만 사용한다.
- 검토 스냅샷: `govuk-user-stories` 구조 `810b85ab3b3a` 본문 `ad98632a17d1`

## 이 문서가 해당 역할에 도움이 되는 이유

제품 에이전트는 기능 설명을 바로 구현 단위로 바꾸기보다, 사용자 목표와 검증 가능한 결과를
작게 나누어야 한다. GOV.UK Service Manual의 사용자 스토리 기준은 역할, 필요, 기대 효과를
분리해 백로그 항목을 쓰도록 요구하므로 우선순위 논의와 구현 범위 조정에 도움이 된다.

## 프로젝트에 적용할 기준

- 스토리는 구현 컴포넌트나 기술 작업명이 아니라 사용자의 역할, 달성하려는 필요, 기대 효과를 중심으로 쓴다.
- 한 스토리가 여러 화면, 권한, 데이터 흐름, 예외 처리를 동시에 포함하면 더 작은 검증 단위로 나눈다.
- 수용 조건은 "구현했다"가 아니라 사용자가 관찰할 수 있는 화면 결과, 상태 변화, 오류 처리로 적는다.
- 비기능 요구사항은 별도 항목으로 분리하되, 성능·접근성·보안처럼 완료 판단에 필요한 기준은 스토리와 연결한다.
- 에픽, 스토리, 작업의 경계를 분명히 해 에이전트가 큰 목표를 임의로 구현 범위로 확장하지 않게 한다.
- 백로그 정제 시 기존 동작 유지, 비목표, 나중에 할 일을 함께 남겨 불필요한 리팩터링을 줄인다.

## 주의할 점

- 사용자 스토리 형식을 맞췄다는 이유만으로 실제 사용자 니즈가 검증됐다고 보지 않는다.
- "관리자로서", "개발자로서"처럼 내부 역할만 반복되면 최종 사용자의 가치가 가려질 수 있다.
- 모든 기술 작업을 억지로 사용자 스토리로 바꾸면 운영·품질 작업의 판단 기준이 흐려질 수 있다.
- 수용 조건이 API 필드나 내부 함수 호출에만 묶이면 프런트엔드와 QA가 같은 완료 기준을 공유하기 어렵다.

## 에이전트가 사용할 때의 체크리스트

- 이 스토리가 누구의 어떤 필요를 다루는지 한 문장으로 설명할 수 있는가?
- 사용자가 얻는 결과와 사업·운영 측면의 기대 효과가 분리되어 있는가?
- 한 PR에서 검증 가능한 크기로 스토리가 나뉘어 있는가?
- 수용 조건이 화면, 권한, 데이터, 오류 상태를 관찰 가능한 문장으로 담고 있는가?
- 비목표와 유지해야 할 기존 동작이 명시되어 있는가?
- 기술 작업은 스토리의 하위 작업인지, 별도의 운영·품질 항목인지 구분되어 있는가?
