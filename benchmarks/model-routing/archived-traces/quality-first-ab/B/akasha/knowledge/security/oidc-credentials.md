# 장기 자격증명 대신 OIDC 사용 기준

## 출처

- 출처 id: `gh-actions-oidc`
- URL: https://docs.github.com/en/actions/concepts/security/openid-connect
- 소유자: GitHub
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: CI에서 클라우드 자격증명 저장 방식 판정에만 사용한다.
- 검토 스냅샷: `gh-actions-oidc` 구조 `5b46866f04aa` 본문 `7861dc33006f`

## 이 문서가 해당 역할에 도움이 되는 이유

CI에 클라우드 키를 secret으로 넣는 것은 가장 흔한 장기 자격증명 노출 경로다. OIDC는 그
키를 아예 두지 않고 잡마다 단기 토큰을 받게 한다. 공식 문서가 신뢰 조건을 어떻게 좁히는지
규정하므로, "secret에 키를 넣었다"를 대안과 함께 지적할 수 있다.

## 프로젝트에 적용할 기준

- 클라우드 자격증명을 장기 secret으로 복제하지 않고 OIDC로 단기 토큰을 발급받는다.
- 클라우드 쪽 신뢰 설정에서 어떤 워크플로가 어떤 역할을 맡을 수 있는지 좁게 지정한다.
- `sub` 클레임으로 저장소·환경 단위까지 범위를 제한한다. 조직 전체를 신뢰 대상으로 두지 않는다.
- 필요하면 커스텀 속성 클레임으로 속성 기반 조건을 더한다.
- OIDC로 전환한 뒤 남아 있는 장기 secret을 제거한다.

## 주의할 점

- 신뢰 조건이 넓으면 OIDC를 써도 의미가 줄어든다. 저장소 이름만으로 신뢰하면 포크나 브랜치 조건이 빠질 수 있다.
- `sub` 클레임 형식은 시점에 따라 달라질 수 있다. 신뢰 조건을 작성할 때 현재 형식을 확인한다.
- 이 문서는 자격증명 전달 방식을 다룬다. 워크플로 권한 최소화는 하드닝 문서를 본다.

## 에이전트가 사용할 때의 체크리스트

- 클라우드 키가 장기 secret으로 저장되어 있지 않은가?
- OIDC 신뢰 조건이 저장소·환경 단위로 좁혀져 있는가?
- 브랜치나 환경 조건 없이 저장소 전체를 신뢰하고 있지 않은가?
- 전환 후 남은 장기 secret을 정리했는가?
