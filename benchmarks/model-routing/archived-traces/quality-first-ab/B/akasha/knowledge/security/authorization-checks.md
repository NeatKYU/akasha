- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: 권한 검사 위치와 기본 거부 원칙 판정에만 사용한다.
- 검토 스냅샷: `owasp-authorization` 구조 `5d13fa7663e9` 본문 `2d9295a6a0ee`

## 이 문서가 해당 역할에 도움이 되는 이유

Broken Access Control은 OWASP Top 10 1위 항목이고, 코드 리뷰에서 놓치기 가장 쉬운 결함이다.
"로그인했는가"와 "이 자원에 권한이 있는가"를 혼동한 코드가 특히 잦다. 이 기준은 검사 위치와
기본값을 규정하므로 누락을 위치와 함께 지목할 수 있다.

## 프로젝트에 적용할 기준

- 인가 검사는 서버 측에서 수행한다. 클라이언트 검사는 UX 개선일 뿐 통제가 아니다.
- 모든 요청에서 권한을 확인한다. 대부분의 요청에서만 확인하는 것은 충분하지 않다.
- 정적 자원(이미지, PDF, 클라우드 스토리지)도 동적 엔드포인트와 같은 접근 통제를 받는다.
- 기본값은 거부다. 명시적으로 허용된 것만 통과시키고, 프레임워크 기본값에 의존하지 않는다.
- 부여한 권한마다 왜 필요한지 설명할 수 있어야 한다. 최소 권한을 유지한다.
- 객체 식별자를 노출한다면 **접근할 때마다** 소유권을 확인한다. 한 객체에 접근할 수 있다고 같은 종류의 모든 객체에 접근할 수 있는 것은 아니다.
- 인가 실패를 모두 처리하고, 오류 메시지에 내부 정보를 노출하지 않는다.
- 인가 로직에 단위·통합 테스트를 둔다. 기본 거부 동작과 예외 경로를 테스트한다.

## 주의할 점

- 식별자를 무작위화하는 것은 인가 검사를 대신하지 못한다. 모호함에 기대는 보안이다.
- 역할 기반(RBAC)만으로는 다중 테넌트나 수평 접근 문제에서 역할 폭발이 일어난다. 속성·관계 기반 모델을 검토한다.
- 자동 테스트는 쉬운 결함만 잡는다. 수동 보안 테스트로 보완한다.

## 에이전트가 사용할 때의 체크리스트

- 인가 검사가 서버 측에 있고 모든 요청 경로를 덮는가?
- 로그인 여부 확인을 소유권 확인으로 착각하고 있지 않은가?
- 기본값이 거부인가, 아니면 명시적으로 막지 않은 것이 통과하는가?
- 객체 접근마다 소유권을 확인하는가?
- 정적 자원에도 같은 통제가 적용되는가?
- 인가 실패 경로에 테스트가 있는가?
