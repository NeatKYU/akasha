# Prisma 트랜잭션과 데이터 무결성 기준

## 출처

- 출처 id: `prisma-transactions`
- URL: https://www.prisma.io/docs/orm/prisma-client/queries/transactions
- 소유자: Prisma Data
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: 트랜잭션 경계, 격리 수준, 타임아웃 판정에만 사용한다.
- 검토 스냅샷: `prisma-transactions` 구조 `f9c9d0f0d4c6` 본문 `720a5a7b8930`

## 이 문서가 해당 역할에 도움이 되는 이유

여러 쓰기가 함께 성공하거나 함께 실패해야 하는 조건은 코드만 봐서는 드러나지 않는다.
공식 문서가 무엇이 자동으로 트랜잭션인지, 어떤 형태를 언제 쓰는지, 어떤 설정이 실패를 만드는지
규정하므로 데이터 무결성 조건이 빠진 지점을 짚을 수 있다.

## 프로젝트에 적용할 기준

- 중첩 쓰기와 `createMany`·`updateMany`·`deleteMany` 같은 배치 작업은 이미 트랜잭션이다. 불필요하게 감싸지 않는다.
- 연산 사이에 값을 읽어 판단해야 하면 순차 트랜잭션이 아니라 인터랙티브 트랜잭션을 쓴다.
- 트랜잭션은 짧게 유지한다. 안에서 네트워크 요청이나 느린 쿼리를 실행하지 않는다.
- 쓰기 충돌(P2034)이 발생할 수 있는 경로에는 재시도 로직을 둔다.
- 격리 수준은 데이터베이스마다 기본값과 지원 범위가 다르므로 의존한다면 명시한다.
- `maxWait`·`timeout` 기본값을 넘길 가능성이 있으면 값을 명시하고 근거를 남긴다.

## 주의할 점

- 트랜잭션 안의 `Promise.all`은 병렬로 실행되지 않고 순차 실행된다.
- 긴 트랜잭션은 성능을 해치고 교착 상태를 유발한다. 커넥션을 오래 붙잡는 것도 같은 문제다.
- 격리 수준을 올리면 충돌이 늘어난다. `Serializable`을 쓴다면 재시도가 전제되어야 한다.

## 에이전트가 사용할 때의 체크리스트

- 함께 성공하거나 함께 실패해야 하는 쓰기가 실제로 한 트랜잭션 안에 있는가?
- 이미 트랜잭션인 배치 작업을 불필요하게 감싸지 않았는가?
- 트랜잭션 안에 네트워크 호출이나 느린 쿼리가 들어 있지 않은가?
- 충돌 가능 경로에 재시도가 있는가?
- 격리 수준이나 타임아웃에 의존한다면 명시되어 있는가?
