- 사용 메모: 전송 보안, 스키마 검증, 자원 소모 방어 판정에만 사용한다.

## 이 문서가 해당 역할에 도움이 되는 이유

API 보안 논의는 인증·인가에 몰리지만, 실제 장애는 형식이 어긋난 페이로드나 과도한 크기에서
자주 난다. 이 기준은 전송·스키마·자원 한계를 함께 규정하므로 계약 층 아래의 방어 누락을
지적할 수 있다.

## 프로젝트에 적용할 기준

- 민감 기능, 인증 세션, 민감 데이터 전송은 모두 잘 구성된 TLS로 암호화한다.
- 서버 인증서는 발급자 신뢰, 만료, 폐기 상태, 도메인 일치를 함께 확인한다.
- 구조화된 페이로드는 스키마로 검증한다. 최대 길이와 허용 문자 집합을 정의한다.
- 고정 형식 파라미터는 허용 목록 패턴으로 검증한다.
- 메시지 크기 상한과 CPU·메모리 소모 상한을 둔다. 재귀 구조 페이로드를 검증한다.
- 출력은 데이터로 인코딩해 스크립트로 해석되지 않게 한다.

## 주의할 점

- 스키마 검증은 형식만 본다. 업무 규칙과 권한은 별도 검사가 필요하다.
- XML을 다룬다면 외부 엔티티와 확장 폭탄 공격을 명시적으로 막아야 한다.
- 이 문서는 서비스 경계 방어를 다룬다. 엔드포인트별 인가는 인가 문서를, REST 계약은 REST 보안 문서를 본다.

## 에이전트가 사용할 때의 체크리스트

- 민감 통신이 전부 TLS 위에 있는가?
- 페이로드에 스키마 검증과 크기 상한이 있는가?
- 재귀·중첩 구조가 자원을 소모하는 경로를 막았는가?
- 출력 인코딩이 적용되어 있는가?
