## 이 문서가 해당 역할에 도움이 되는 이유

API 엔드포인트 검토는 "어떤 메서드를 어떤 계약으로 노출하는가"에서 시작한다. 공식 레퍼런스는
지원 메서드, 요청 객체에서 읽을 수 있는 것, 세그먼트 설정이 캐싱에 미치는 영향을 규정하므로
계약이 암묵적으로 남아 있는 지점을 짚을 수 있다.

## 프로젝트에 적용할 기준

- 노출할 HTTP 메서드를 명시적으로 내보낸다. 정의하지 않은 메서드는 자동 처리에 맡기지 말고 의도를 남긴다.
- 동적 세그먼트의 `params`는 promise다. await하지 않고 쓰는 코드를 허용하지 않는다.
- 요청 본문은 `request.json()`·`request.formData()`로 읽고, FormData 값은 전부 문자열이므로 별도 파싱·검증을 거친다.
- 쿠키·헤더는 읽기 전용이다. 설정이 필요하면 새 `Response`를 반환한다.
- 캐싱이 필요한 GET은 세그먼트 설정(`revalidate` 등)으로 명시한다. 기본 동작에 의존하지 않는다.
- CORS 헤더를 개별 핸들러에 흩뿌리지 않고 여러 라우트에 걸치면 공통 설정으로 모은다.

## 주의할 점

- `GET` 핸들러의 기본 캐싱 동작은 Next.js 버전에 따라 바뀌었다. 프로젝트 버전을 확인하고 판정한다.
- 웹훅 수신 핸들러는 본문 파싱 실패를 400으로 다루는 등 오류 경로를 별도로 설계해야 한다.
- 이 문서는 요청·응답 계약을 다루며 인증·인가 자체는 다루지 않는다. 그 판정은 인가·입력 검증 문서를 근거로 한다.

## 에이전트가 사용할 때의 체크리스트

- 노출된 메서드가 의도한 목록과 일치하는가?
- `params`를 await하고 있는가?
- FormData·JSON 본문에 검증 단계가 있는가?
- 캐싱 의도가 세그먼트 설정으로 드러나는가, 아니면 기본값에 기대고 있는가?
- 오류 응답이 상태 코드와 함께 정의되어 있는가?
