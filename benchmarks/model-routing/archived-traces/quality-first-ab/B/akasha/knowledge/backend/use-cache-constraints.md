# use cache 제약과 캐시 키 기준

## 출처

- 출처 id: `next-use-cache`
- URL: https://nextjs.org/docs/app/api-reference/directives/use-cache
- 소유자: Vercel
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: use cache 범위 안에서 허용되지 않는 것과 캐시 키 구성 판정에만 사용한다.
- 검토 스냅샷: `next-use-cache` 구조 `990c43e4916a` 본문 `0c3d473edee6`

## 이 문서가 해당 역할에 도움이 되는 이유

캐시 경계 안에서 요청 데이터를 읽으면 빌드는 통과하고 운영에서 깨질 수 있다. 또 클로저로
잡힌 변수가 캐시 키에 들어가는 것을 모르면 의도치 않은 캐시 분리나 공유가 생긴다.
공식 레퍼런스가 키 구성과 제약을 규정한다.

## 프로젝트에 적용할 기준

- `use cache`를 붙인 함수·컴포넌트는 async여야 한다. 파일 최상단에 두면 모든 export가 대상이 된다.
- 캐시 키는 빌드 ID, 함수 식별자, 직렬화된 인자로 구성된다. **외부 스코프에서 잡힌 변수도 인자로 묶여 키에 들어간다.**
- 캐시 범위 안에서 `cookies()`·`headers()`·`searchParams`를 읽지 않는다. 밖에서 읽어 인자로 넘긴다.
- 인자와 반환값은 직렬화 가능해야 한다. 클래스 인스턴스, 함수, Symbol, URL 인스턴스는 인자로 쓸 수 없다.
- `children` 같은 슬롯은 내부에서 들여다보지 않으면 통과시킬 수 있고 캐시 항목에 영향을 주지 않는다.
- 모든 `use cache` 범위에 `cacheLife`를 명시한다. 생략하면 기본 프로필이 적용되어 수명이 호출 지점에서 드러나지 않는다.

## 주의할 점

- 요청 API 제약은 호출 스택을 따라 적용된다. 캐시 함수가 부르는 헬퍼가 읽어도 같은 오류가 난다.
- 동적 라우트에서는 `next build`를 통과하고 실행 시점에 실패할 수 있다.
- 서버리스에서는 인메모리 캐시가 요청 간에 유지되지 않을 수 있다. 배포가 바뀌면 캐시 키의 빌드 ID가 달라져 전부 무효가 된다.
- `React.cache`는 `use cache` 경계 안에서 격리된다. 바깥에서 저장한 값이 보이지 않는다.
- 빌드가 멈추면 캐시 경계 밖에서 만든 미해결 Promise를 안에서 기다리는 경우다.

## 에이전트가 사용할 때의 체크리스트

- 캐시 범위 안에서 쿠키·헤더·searchParams를 읽고 있지 않은가?
- 클로저로 잡힌 변수가 의도한 캐시 키 분리를 만드는가?
- 인자와 반환값이 직렬화 가능한가?
- `cacheLife`가 명시되어 있는가?
- 서버리스에서 캐시 지속을 전제로 설계하고 있지 않은가?
