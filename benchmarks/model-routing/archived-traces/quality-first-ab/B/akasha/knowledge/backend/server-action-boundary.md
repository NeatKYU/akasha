## 이 문서가 해당 역할에 도움이 되는 이유

Server Action은 코드상 함수처럼 보이지만 **실제로는 누구나 POST할 수 있는 엔드포인트**다.
이 사실이 자주 누락되어 UI에서 폼을 감췄다는 이유로 인가를 생략하는 코드가 나온다.
공식 문서가 프레임워크 보호와 애플리케이션 책임을 나눠 규정하므로 그 경계를 근거로 판정할 수 있다.

## 프로젝트에 적용할 기준

- 모든 Server Action을 신뢰할 수 없는 진입점으로 취급한다. 인증된 페이지에서만 폼을 렌더한다는 것은 보안 경계가 아니다.
- 액션 안에서 인증과 인가를 각각 확인한다. 세션 존재 확인만으로 소유권 확인을 대신하지 않는다.
- `FormData`, 쿼리 파라미터, 헤더를 신뢰하지 않고 검증한다.
- 클라이언트에게는 대상 식별자와 변경분만 받고, 나머지는 세션 기준으로 신뢰할 수 있는 곳에서 다시 읽는다.
- 반환값은 화면이 렌더할 형태로 좁힌다. 데이터베이스 레코드를 그대로 반환하지 않는다.
- 삭제 같은 파괴적 작업은 상향된 세션 확인이나 재인증을 고려하고, 확인이 누락되면 조용히 통과하지 않고 실패시킨다.
- 프록시·CDN 도메인이 있으면 허용 origin을 설정한다.

## 주의할 점

- 스키마 검증(zod 등)은 입력의 **모양**만 확인한다. 형식이 올바른 객체가 남의 행을 가리킬 수 있다.
- 액션은 클라이언트당 순차 실행된다. `Promise.all`로 병렬화하려는 코드는 의도대로 동작하지 않는다.
- 인라인 액션이 캡처한 변수는 암호화되어 클라이언트로 간다. 다중 인스턴스 배포에서는 암호화 키를 인스턴스 간에 고정해야 한다.
- 배포마다 액션 ID가 바뀔 수 있어 이전 빌드를 쓰는 클라이언트가 실패할 수 있다. 재시도 경로를 UI에 남긴다.

## 에이전트가 사용할 때의 체크리스트

- 액션 첫머리에 인증 확인이 있는가?
- 인가가 소유권 수준까지 확인하는가, 아니면 로그인 여부만 보는가?
- 클라이언트가 보낸 객체를 그대로 신뢰해 갱신 대상을 정하지 않는가?
- 반환값이 화면에 필요한 필드로 좁혀져 있는가?
- 파괴적 작업에 추가 확인이 있는가?
- 검증 실패가 조용히 통과되지 않고 오류로 드러나는가?
