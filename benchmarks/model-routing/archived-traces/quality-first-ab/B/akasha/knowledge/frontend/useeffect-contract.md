# useEffect 의존성과 정리 함수 계약

## 출처

- 출처 id: `react-useeffect`
- URL: https://react.dev/reference/react/useEffect
- 소유자: Meta
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: useEffect 의존성 배열과 정리 함수의 계약 위반 판정에만 사용한다.
- 검토 스냅샷: `react-useeffect` 구조 `7e775b9f3756` 본문 `8ac0400c693c`

## 이 문서가 해당 역할에 도움이 되는 이유

Effect를 쓰기로 결정한 뒤에도 오판이 잦은 지점이 남는다. 의존성에 무엇을 넣어야 하는지,
정리 함수가 언제 도는지, 개발 모드에서 두 번 실행되는 것이 버그인지가 대표적이다.
공식 레퍼런스는 이를 계약으로 규정하므로 "동작은 하지만 계약 위반"인 코드를 가려낼 수 있다.

## 프로젝트에 적용할 기준

- Effect 안에서 참조하는 모든 반응형 값(props, state, 컴포넌트 본문에서 선언한 변수·함수)을 의존성 배열에 넣는다.
- 컴포넌트 밖에서 선언한 상수처럼 반응형이 아닌 값은 의존성에 넣지 않는다.
- 정리 함수는 설정(setup)이 한 일을 되돌린다. 사용자가 "설정 1회"와 "설정→정리→설정"을 구분할 수 없어야 한다.
- 매 렌더마다 새로 만들어지는 객체·함수를 의존성에 넣지 않는다. Effect 안에서 만들고 원시값에 의존한다.
- state를 갱신할 때 이전 값을 읽어야 하면 갱신 함수 형태(`setCount(c => c + 1)`)를 써서 자기 의존성을 만들지 않는다.
- 의존성 린터 경고를 주석으로 억누르지 않는다. 의존성이 필요 없음을 리팩터링으로 증명한다.
- 의존성 배열은 명시적 배열, 빈 배열, 생략 중 하나이며 생략은 대개 실수다.

## 주의할 점

- 개발 모드 Strict Mode에서 설정→정리→설정이 한 번 더 도는 것은 버그가 아니라 정리 함수 검증이다. 이 때문에 문제가 생기면 정리 함수가 부족한 것이다.
- 정리 함수는 언마운트뿐 아니라 **의존성이 바뀔 때마다** 이전 값으로 먼저 실행된다.
- 의존성 비교는 `Object.is`다. 값이 같아 보여도 참조가 다르면 다시 실행된다.
- 린터를 만족시키려고 의존성을 형식적으로 채우면 원인이 가려질 수 있다. 왜 그 값이 반응형인지부터 확인한다.

## 에이전트가 사용할 때의 체크리스트

- Effect가 참조하는 반응형 값이 모두 의존성 배열에 있는가?
- 의존성에 매 렌더 새로 생기는 객체나 함수가 들어 있지 않은가?
- 정리 함수가 설정이 만든 구독·연결·타이머를 실제로 해제하는가?
- Effect가 자기 의존성에 있는 state를 갱신해 무한 루프를 만들지 않는가?
- 의존성 린터 경고를 억제하는 주석이 있는가? 있다면 근거가 코드로 증명되는가?
- 의존성 배열이 실수로 생략되어 매 커밋마다 실행되고 있지 않은가?
