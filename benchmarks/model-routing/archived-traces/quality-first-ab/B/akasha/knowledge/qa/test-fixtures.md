# 테스트 fixture 설계 기준

## 출처

- 출처 id: `playwright-fixtures`
- URL: https://playwright.dev/docs/test-fixtures
- 소유자: Microsoft
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: fixture와 before/after 훅 선택, 스코프 판정에만 사용한다.
- 검토 스냅샷: `playwright-fixtures` 구조 `29fdd78261cf` 본문 `b445ae3b1f45`

## 이 문서가 해당 역할에 도움이 되는 이유

테스트 격리는 원칙만으로는 지켜지지 않고 준비·정리 코드를 어디에 두느냐로 결정된다.
`beforeEach`에 흩어진 준비 코드는 어떤 테스트가 무엇에 의존하는지 감추고, 정리가 빠지면
순서 의존 실패가 된다. 공식 문서가 fixture와 훅의 차이를 규정하므로 배치 문제를 지적할 수 있다.

## 프로젝트에 적용할 기준

- 준비와 정리가 짝을 이루는 상태는 훅이 아니라 fixture로 만든다. 준비와 정리가 같은 자리에 있어야 한다.
- fixture는 테스트가 요청할 때만 초기화된다. 모든 테스트에 필요한 것이 아니면 훅으로 전역화하지 않는다.
- 테스트마다 격리되어야 하는 자원은 test 스코프, 여러 테스트가 충돌 없이 공유할 수 있는 자원은 worker 스코프로 둔다.
- 로깅·계측처럼 모든 테스트에 붙어야 하는 관심사는 자동 fixture로 만든다.
- 느린 fixture는 별도 timeout을 지정해 테스트 timeout을 잠식하지 않게 한다.
- 설정만을 위해 `describe`로 테스트를 묶지 않는다. fixture 조합으로 표현한다.

## 주의할 점

- worker 스코프 자원을 여러 테스트가 변경하면 격리가 깨진다. 공유해도 되는지 먼저 확인한다.
- 자동 fixture는 요청하지 않아도 실행되므로 비용이 모든 테스트에 붙는다.
- 이 문서는 fixture 구조를 다룬다. locator·assertion 작성은 E2E 테스트 기준 문서를 근거로 한다.

## 에이전트가 사용할 때의 체크리스트

- 준비 코드에 대응하는 정리가 같은 자리에 있는가?
- 전역 훅으로 둔 준비가 실제로 모든 테스트에 필요한가?
- worker 스코프로 공유한 자원을 테스트가 변경하지 않는가?
- 느린 준비 작업에 별도 timeout이 지정되어 있는가?
- 설정 목적만으로 `describe` 묶음을 만들지 않았는가?
