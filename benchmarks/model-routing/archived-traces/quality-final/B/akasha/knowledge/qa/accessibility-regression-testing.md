- 사용 메모: 접근성 회귀 탐지와 브라우저 테스트 범위 조정 기준으로만 사용한다.
- 검토 스냅샷: `playwright-accessibility-testing` 구조 `1d178a574f7b` 본문 `ac8dfc82e7d2`

## 이 문서가 해당 역할에 도움이 되는 이유

QA 에이전트는 접근성을 수동 점검의 부록으로 두지 말고, 반복 가능한 회귀 신호로 관리해야 한다.
Playwright의 접근성 테스트 문서는 자동 검사 도구를 브라우저 테스트 흐름 안에 배치하되, 자동화가
모든 접근성 문제를 찾지는 못한다는 한계를 전제한다. 이 기준은 UI 변경 PR에서 빠르게 깨지는
라벨, landmark, contrast, focus 관련 문제를 조기에 분류하는 데 유용하다.

## 프로젝트에 적용할 기준

- 주요 사용자 경로에는 접근성 자동 검사를 smoke 수준으로 포함하고, 위반 항목은 테스트 결과에 남긴다.
- 자동 검사 범위는 페이지 전체와 핵심 컴포넌트 단위 중 회귀 위험이 큰 쪽을 선택해 과도한 실패 노이즈를 줄인다.
- 테스트는 자동 검사 결과만 보지 않고 키보드 이동, focus 순서, 대체 텍스트, 오류 메시지 노출을 함께 확인한다.
- 알려진 예외는 규칙 비활성화보다 명시적 근거와 후속 처리 항목으로 관리한다.
- 접근성 테스트 실패는 스냅샷 업데이트처럼 자동 승인하지 않고, 사용자 영향과 수정 비용을 함께 triage한다.
- 컴포넌트 재사용이 많은 영역은 한 곳의 접근성 회귀가 여러 화면으로 퍼질 수 있으므로 공유 UI 변경을 우선 점검한다.

## 주의할 점

- 자동 접근성 검사는 보조 기술 사용 경험 전체를 대체하지 못한다.
- 테스트 환경의 색상 모드, viewport, 언어, 동적 콘텐츠 상태가 실제 사용자 조건과 다르면 누락이 생길 수 있다.
- 한 번에 모든 페이지를 검사하면 CI 시간이 늘고 중요 실패가 묻힐 수 있다.
- 접근성 위반을 임시 허용할 때는 만료 조건 없이 suppression만 남기지 않는다.

## 에이전트가 사용할 때의 체크리스트

- 이번 변경이 heading, label, landmark, button name, form error, focus 흐름 중 무엇을 바꾸는가?
- 자동 접근성 검사를 넣을 가장 작은 안정 범위가 페이지인지 컴포넌트인지 판단했는가?
- 키보드만으로 주요 작업을 시작, 완료, 취소할 수 있는가?
- 오류와 로딩 상태가 화면 텍스트와 보조 기술 양쪽에서 인식 가능한가?
- 알려진 위반은 근거, 영향 범위, 제거 조건이 함께 기록되어 있는가?
- 실패 보고서가 접근성 규칙 이름, 화면 상태, 재현 명령을 포함하는가?
