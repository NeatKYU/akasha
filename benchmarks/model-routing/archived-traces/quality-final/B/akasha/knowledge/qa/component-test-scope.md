- 출처 id: `playwright-components`
- URL: https://playwright.dev/docs/test-components
- 소유자: Microsoft
- 권위: primary
- 라이선스 메모: 메타데이터, 링크, 짧은 출처 표기 요약만 사용한다. 원문을 복제하지 않는다.
- 사용 메모: E2E와 컴포넌트 테스트의 경계 판정에만 사용한다.
- 검토 스냅샷: `playwright-components` 구조 `d223d3bfac22` 본문 `b35e8f54d354`

## 이 문서가 해당 역할에 도움이 되는 이유

"이건 E2E로 짜야 하나 컴포넌트 테스트로 짜야 하나"는 자주 취향 논쟁이 된다. 각 방식이
무엇을 실제로 검증하고 무엇을 할 수 없는지 규정되면 근거 있는 배치가 가능하다.

## 프로젝트에 적용할 기준

- 컴포넌트 테스트는 실제 브라우저에서 컴포넌트를 격리해 렌더하고 실제 클릭과 레이아웃을 거친다. 단위 테스트의 모의 렌더와 다르다.
- 여러 페이지를 오가는 사용자 여정은 E2E로, 단일 컴포넌트의 상태·상호작용은 컴포넌트 테스트로 나눈다.
- 시나리오는 story 파일의 named export로 두고 컴포넌트 옆에 둔다. 테스트 안에 인라인 JSX를 쓰지 않는다.
- 검증은 관찰 가능한 DOM 상태로 한다. 콜백 호출 여부를 경계 너머로 확인하려 하지 않는다.
- 테스트와 assertion은 Node에서, story와 그 상태는 브라우저에서 돈다. 이 경계를 전제로 설계한다.

## 주의할 점

- 컴포넌트 인스턴스의 메서드나 내부 상태에 직접 접근할 수 없다. 그런 검증이 필요하면 설계를 다시 본다.
- 자체 dev server가 필요하다. CI 구성에 이 전제가 반영되어야 한다.
- 프레임워크에 따라 지원 정도가 다르다. 프로젝트 스택에서 실제로 되는지 확인한다.

## 에이전트가 사용할 때의 체크리스트

- 이 테스트가 검증하려는 것이 단일 컴포넌트의 동작인가, 여러 화면을 오가는 여정인가?
- 내부 상태나 콜백 호출이 아니라 관찰 가능한 DOM 결과를 검증하는가?
- 시나리오가 story로 분리되어 있는가?
- 컴포넌트 테스트로 E2E를 대체하려 하고 있지 않은가?
