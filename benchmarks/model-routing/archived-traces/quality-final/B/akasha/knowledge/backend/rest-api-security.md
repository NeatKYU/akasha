## 이 문서가 해당 역할에 도움이 되는 이유

백엔드 에이전트가 "이 API는 안전한가"를 취향이 아니라 규범으로 판정하려면 항목별 기준이 필요하다.
OWASP 기준은 엔드포인트마다 확인할 수 있는 형태로 되어 있어 위반을 위치와 함께 지목할 수 있다.

## 프로젝트에 적용할 기준

- 비공개 REST 서비스는 **엔드포인트마다** 접근 통제를 수행한다. 프론트엔드 차단은 보안 경계가 아니다.
- 허용 HTTP 메서드를 allowlist로 정하고, 그 외에는 405로 응답한다. 허용된 메서드마다 인가를 다시 확인한다.
- API 키·토큰·비밀번호를 쿼리 문자열이나 경로에 넣지 않는다. 본문이나 헤더로 전달한다.
- 오류 응답에 스택 트레이스·내부 경로·디버그 정보를 넣지 않고 일반화된 메시지를 반환한다.
- 상태 코드를 의미에 맞게 쓴다. 인증 실패는 401, 권한 없음은 403, 미지원 메서드는 405, 미지원 콘텐츠 타입은 415, 한도 초과는 429다.
- 요청 `Content-Type`이 예상과 다르면 406 또는 415로 거절하고, 응답 `Content-Type`에 `Accept` 헤더를 그대로 복사하지 않는다.
- CORS는 필요할 때만 켜고 허용 origin을 구체적으로 지정한다. 민감한 작업에 와일드카드를 쓰지 않는다.
- 관리용 엔드포인트는 공개 인터넷에 노출하지 않는다.

## 주의할 점

- JWT를 쓴다면 토큰이 지정한 알고리즘을 신뢰해 검증하지 않는다. `alg: none`을 허용하지 않는다.
- API 키만으로 고가치 자원을 보호하지 않는다. 키는 쉽게 유출된다.
- 검증 실패가 초당 수백 건 발생하면 공격 신호일 수 있다. 로그로 남기되 로그 자체를 정제한다.
- 이 문서는 REST 계약 층을 다룬다. 인가 모델 설계는 인가 기준 문서를, 입력 검증 상세는 입력 검증 문서를 본다.

## 에이전트가 사용할 때의 체크리스트

- 모든 비공개 엔드포인트가 자체적으로 접근 통제를 하는가?
- 허용 메서드 목록이 있고 그 외 요청이 405로 거절되는가?
- 민감값이 URL에 실려 로그·브라우저 기록에 남지 않는가?
- 오류 응답이 내부 정보를 노출하지 않는가?
- 상태 코드가 의미에 맞게 쓰이고 있는가?
- CORS 허용 origin이 구체적인가?
