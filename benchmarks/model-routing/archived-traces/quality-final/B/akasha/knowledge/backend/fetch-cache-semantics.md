- 사용 메모: 서버에서 수행하는 fetch의 캐시 옵션과 개인화 데이터 판정에만 사용한다.
- 검토 스냅샷: `next-fetch-reference` 구조 `3c58878332dc` 본문 `93734e385274`

## 이 문서가 해당 역할에 도움이 되는 이유

서버 fetch의 `cache` 옵션은 브라우저 HTTP 캐시가 아니라 프레임워크의 영속 캐시를 가리킨다.
이 차이를 놓치면 개인화된 응답이 다른 사용자에게 재사용되는 사고로 이어진다. 공식
레퍼런스가 각 옵션의 의미와 매칭 기준을 규정한다.

## 프로젝트에 적용할 기준

- `cache` 옵션은 서버 측 영속 캐시 동작을 정한다. 브라우저 캐시 의미로 읽지 않는다.
- 캐싱은 opt-in이다. `force-cache`를 설정하면 `POST`나 `authorization`·`cookie` 헤더를 보내는 요청까지 캐시된다. 개인화 응답에 붙이지 않는다.
- 캐시 매칭은 URL·메서드·헤더·본문으로 이뤄진다. 이 중 하나라도 다르면 별도 항목이 된다.
- 수명이 필요하면 `next.revalidate`를 초 단위로 지정한다. `0`은 캐시하지 않음, `false`는 무기한이다.
- 온디맨드 무효화가 필요하면 `next.tags`로 태그를 붙인다.
- `{ revalidate: n, cache: 'no-store' }` 처럼 충돌하는 조합은 둘 다 무시된다. 하나만 쓴다.

## 주의할 점

- 같은 라우트에서 같은 URL에 서로 다른 `revalidate`를 주면 더 낮은 값이 적용되고, 라우트 전체 재검증 주기까지 내려간다.
- GET 요청은 한 번의 렌더 패스 안에서 자동으로 메모이즈된다. 이는 영속 캐시와 다른 개념이다. Route Handler에는 적용되지 않는다.
- 개발 환경에는 HMR 캐시가 있어 `no-store` 요청도 갱신되지 않아 보일 수 있다. 캐시 문제를 진단할 때 혼동하지 않는다.

## 에이전트가 사용할 때의 체크리스트

- 개인화된 응답에 `force-cache`가 붙어 있지 않은가?
- 인증 헤더나 쿠키를 보내는 요청이 캐시 대상이 되어 있지 않은가?
- 캐시 수명이 명시되어 있는가?
- 충돌하는 캐시 옵션 조합이 없는가?
- 개발 환경 HMR 캐시를 실제 캐시 동작으로 오해하고 있지 않은가?
