아카샤 채점 검수

18개 답안을 제가 정답 키 기준으로 초안 채점했습니다. 선님은 아래 질문 13개에만 답하시면 라벨링이 끝납니다. 나머지 확실한 판정은 훑어보고 이상하면 지적해주세요.

답하는 방법
  • 제 제안이 다 맞으면 채팅에 “전부 제안대로” 한 마디면 됩니다.
  • 일부만 다르면 번호로: 예) “Q3은 FP 아님, Q13은 인정, 나머지 제안대로”
  • 확실 판정(✅/❌)이 틀렸으면: 예) “R09의 K3은 미커버로”

확인 필요 질문 (13개)

각 질문에는 제 제안(기울임 없이 굵게)이 있습니다. 동의하면 넘어가면 됩니다.

Q1 · R06 (r2) — 결함 3개를 다 언급했지만 전부 “위반 아님”으로 분류
위반: 없음. 선택된 접근성 문서는 APG(정보 제공용)여서 … 규범적 “위반”으로 확정할 근거가 배정 범위에 없었습니다.

버튼→div, role 제거, 확인 버튼 문제를 표에 다 적었지만 전부 “지식베이스에 근거 없음”으로 내렸습니다. 검토의 임무는 위반을 잡는 것이므로 —

제안: K1·K2·K3 모두 미커버 (언급했어도 위반 분류 실패 = recall 실패)

Q2 · R13 (r2) — role/aria 제거를 “근거 있는 확인” 섹션에 서술
기존 role="dialog", aria-modal, aria-labelledby가 제거되었습니다. … 이것만으로 규범적 “위반”으로 판정하지 않았습니다.

제안: K2 미커버 (제거 사실은 정확히 봤지만 위반으로 분류하지 못함)

Q3 · R15 (r2) — 없었던 alertdialog를 “제거했다”고 서술
삭제 확인 흐름에서 alertdialog 역할, 제목 연결, 경고문 설명 연결, 모달 의미를 제거했습니다.

alertdialog와 경고문 연결(aria-describedby)은 변경 전에도 없었습니다. 같은 문장에 실제 제거된 것(제목 연결·모달 의미)도 섞여 있어서 K2는 커버로 인정하되 —

제안: trap T2 발생 (허위 “제거” 서술 = FP 1건)

Q4 · R15 (r2) — 원래 없던 포커스/Escape를 위반으로 판정
열 때 포커스 이동, Tab/Shift+Tab 순환, Escape 닫기 … 구현되어 있지 않습니다. (위반 표에 배치)

제안: trap T1 발생 (변경 전에도 없던 것을 이번 변경의 위반으로 = FP 1건)

Q5 · R18 (r2) — “이전에도 있던 문제”라고 쓰면서 위반 표에 배치 ①
alertdialog 역할 및 … aria-describedby가 없습니다. 이 문제는 이번 변경 이전에도 있었던 것으로 보입니다. (위반 표에 배치)

본문은 pre-existing이라고 인정하는데 분류는 위반입니다. 섹션 배치가 곧 분류라고 보면 —

제안: FP 1건 (관대하게 보면 세이프 — 선님 판단에 맡깁니다)

Q6 · R18 (r2) — 같은 패턴 ②: 포커스 트랩 부재를 위반 표에 배치
포커스 이동, Tab/Shift+Tab 트랩, Escape 닫기 … 가 없습니다. 이 역시 이번 diff에서 새로 생긴 문제는 아닙니다. (위반 표에 배치)

제안: trap T1 발생 (Q5와 같은 기준으로 판정해주세요)

Q7 · R05 (r3) — 새로 추가된 userId의 검증 부재를 위반으로
추가된 JSON userId에 파싱 뒤 검증 단계가 없습니다.

trap T1은 “base에도 있던 body.name 검증 부재”를 잡는 함정인데, 이 응답은 diff가 새로 추가한 userId만 지적했습니다. 새 입력의 검증 부재는 introduced로 변명 가능하므로 —

제안: T1 아님 (OK-기타로 인정)

Q8 · R08 (r3) — base에도 있던 문제 2개를 위반으로
① name과 userId를 검증 없이 DB 생성에 사용합니다. ② ORM 생성 결과를 DTO 필터링 없이 그대로 반환합니다.

①은 name까지 묶었으므로(name은 base에도 검증 없이 사용) trap 대상이고, ②의 응답 반환 방식은 diff에서 아예 안 바뀌었습니다.

제안: ① T1 발생 + ② FP 1건 (합계 FP 2건)

Q9 · R14 (r3) — “name·userId 검증 없음”을 위반으로

제안: T1 발생 (Q8-①과 같은 유형, name 포함)

Q10 · R16 (r3) — “name·userId 검증 없이 영속화”를 위반으로

제안: T1 발생 (같은 유형)

Q11 · R11 (r3) — ownerId 문제를 ‘입력 검증’ 프레임으로만 잡음
외부 JSON 입력이 검증 없이 저장 경로에 사용됨 (위반) … 인증 주체와 객체 소유자의 일치 여부를 판정할 인가 모델 기준은 제공하지 않는다 (공백)

정답 K1의 핵심인 “인가 상실”은 공백으로 미루고, 같은 줄을 검증 문제로만 위반 처리했습니다. 같은 결함 위치를 잡긴 했으므로 —

제안: K1 커버 인정, 단 근거 적합성은 ‘부적합’ (엄격하게 미커버로 보셔도 됩니다)

Q12 · R11 (r3) — count()/격리 문제를 공백으로만 처리
… 현재 파일 범위만으로 seed/cleanup 유무를 확정할 수 없어 위반으로 확정하지 않았다.

K8(web-first 후퇴)의 정답 분류는 위반입니다. toBeVisible → 즉시 count()로 바뀐 건 diff에 명백한데 위반 확정을 거부했으므로 —

제안: K8 미커버 (R06의 Q1과 같은 기준)

Q13 · 정책 질문 (r3 공통) — @unique 공백 처리를 K3 커버로 인정할까?

K2(@unique 제거 = 중복 허용 효과 확정)는 18건 전원 실패입니다 — 이 판정용 지식 문서가 측정 시점에 아직 없었으므로 예상된 결과이고, 버전 간 차이를 만들지 않습니다. 문제는 K3(migration·cardinality 근거 공백 분리): R09·R12는 “카디널리티 계약·기존 데이터 미제공”을 명시해 확실 커버인데, R02·R04·R05·R08·R14·R16은 “판정 기준이 없다”고 뭉뚱그려 공백 처리만 했습니다.

제안: 관대 인정 (공백으로 분리한 행위 자체를 커버로) — 엄격하게 가면 6건 모두 K3 미커버가 됩니다. 하나만 골라주세요.

확실 판정의 근거 (훑어보기용)

전 응답 공통으로 확실한 것만 요약합니다. 원문 전문은 라벨링-시트-r2.md / 라벨링-시트-r3.md에 있습니다.

r2에서 확실 커버로 처리한 것

R01·R03·R07·R10·R13(K1·K3)·R15·R17·R18은 모두 아래 3종 위반을 diff 근거와 함께 정확히 지적했습니다:

K1 열기 button→div K2 role/aria 제거 K3 확인 button→div
예 (R17): “버튼을 클릭 전용 <div>로 변경해 키보드 조작이 불가능합니다 … role="dialog", aria-modal="true", aria-labelledby를 제거하여 …” — 3건 모두 introduced_by_diff로 명시

C1('use client' 적절 확인)은 R01·R10·R13만 있음 — 선택 크레딧이라 나머지는 감점 아님.

r3에서 확실 커버로 처리한 것

R02·R04·R05·R08·R09·R12·R14·R16은 아래 6종을 정확히 지적했습니다 (R09는 tests 3건을 finding 하나로 묶었지만 각각 언급):

K1 ownerId=body.userId 인가 K4 write-all K5 SHA→@v4 K6 CSS locator K7 waitForTimeout K8 즉시 count()

전원 공통 미커버: K2 @unique 중복 허용 효과 — 당시 지식 문서 부재로 예상된 패턴 (버전 비교에 영향 없음).

R11만 예외적으로 약함: K6(locator) 언급 자체가 없고, K1·K8을 공백으로 미룸.
