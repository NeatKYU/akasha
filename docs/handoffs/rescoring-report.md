### 결론 1 — 헤드라인 +9.58%p의 재해석

**이 표본에서** A→B2의 정답 커버리지는 macro로 거의 동일(94.4→95.2%)하고 micro로는
소폭 낮다(96.7→93.3%, R11의 2키 미커버). 뚜렷한 차이는 **FP 8건→0건** — A는 6개 run 중
5개에서 pre-existing 문제(포커스 부재, name 검증 부재, 응답 미필터링, alertdialog 부재)를
이번 변경의 위반으로 보고했고, B 계열은 전부 분리했다. 기존 regex 지표는 FP를 측정하지
못하므로(+`input-validation` 항목은 FP 응답 1건에 점수를 줌), +9.58%p는 방향과 무관하게
**다른 것을 잰 수치**였다. 정확한 서술: "이 표본에서 FP가 8→0으로 감소했고, 커버리지는
집계 방식에 따라 거의 비슷하거나 소폭 낮다." ("precision 개선"이라는 표현은 finding별
TP/FP 저장 이후에만 사용한다 — 라운드 2 수용.)

### 결론 2 — B1/B2 배치 차이: 후보가 달랐음은 확실, 기여량 귀속은 불가

키 기준 B1 83.3% vs B2 95.2%(macro). B1의 하락은 R06 한 건(r2 결함 3개를 전부 언급하고도
"APG는 informative"라며 위반 0건으로 후퇴)이 지배한다. 형식 증거(B1 Markdown/B2 JSON)로
두 배치의 후보가 달랐음은 확실하다. 그러나 n=3에 작업 트리 provenance가 없으므로 12.08%p
regex 차이 중 후보 차이와 실행 분산의 기여량은 **귀속 불가**로 남긴다. 인과 서술("0.15.0이
오탐을 제거했다")은 provenance 스탬프를 갖춘 재실행 후에만 가능하다. (라운드 1 초판의
"후보 차이가 주원인" 표현은 과잉 귀속이라는 라운드 2 지적을 수용해 정정했다.)

### 결론 3 — regex 채점기는 사람 라벨과 26.7% 불일치

90쌍(18 run × 매핑 키) 중 24쌍 불일치 (r2 10, r3 14). 양방향 오류:

- 과소 인정 22쌍: 정답을 맞혔지만 rubric 단어와 표현이 다름 — 대표적으로 `screen-reader`
  항목은 "스크린리더" 단어를 요구하는데 JSON 응답은 role/aria로 서술 (r2-K2에서 6쌍),
  `migration-gap`·`sha`·`web-first`도 동일 유형.
- 과대 인정 2쌍: R06 — 주제 단어만 있으면 위반 분류 실패여도 통과 (r2-K1·K3).

### 결론 4 — 계약 JSON에서 기계 채점기는 사람과 100% 일치

계약 JSON 응답 6건(33개 키 판정)에서 diff_evidence 앵커 기계 매처가 사람 라벨과
**33/33 일치**. 중요 실증: basis(설명 문장)까지 매칭에 넣으면 31/33으로 떨어진다 —
R11의 waitForTimeout finding basis에 "locator·web-first를 써야 한다"는 처방 문구가
있어 K6·K8이 교차 오인정됐다. **증거 필드만 앵커로 쓰는 것이 정확도의 조건**이며,
이는 diff_evidence 계약의 가치를 데이터로 뒷받침한다.
Markdown 응답 12건은 기계 채점 불가 — JSON 계약이 채점 자동화의 전제임을 함께 보여준다.

## 수용 기준 판정 — 라운드 2 반영 (2026-08-24)

Codex 검증(`scratchpad/codex-round2` → 아래 요약): **수치는 전부 재현·확인**
(배치 집계, 불일치 24/90, 기계 채점 33/33 vs basis 포함 31/33, 증거 전용 앵커 결론 포함).
그러나 초판 보고의 "5개 기준 전부 통과"는 기각됐다 — 기준 2·4·5 미충족과
결론 2의 과잉 귀속(기각 조건 해당)이 지적됐다. 지적 수용 후 즉시 보완한 상태는:

| 기준 | 초판 | Codex 판정 | 보완 후 |
| --- | --- | --- | --- |

| 2. finding별 역추적 | 통과 | **미통과** — finding→키 매핑·근거 적합성 미저장 | **보완**: `key-scorer-output.json`(JSON 6건, 기계 생성) + `finding-audit-markdown.json`(12건, 사람 확정 판정 기반) |
| 3. 계약 유효성 비합산 | 통과 | 통과(오프라인 한정) | 동일 — runner 분리는 재측정 전 필수 과제로 이월 |

| 5. B 차이 설명/불가 구분 | 통과 | **미통과** — "후보 차이 주원인"은 과잉 귀속 | **보완**: 결론 2 정정 — 후보 상이 사실만 확정, 기여량 귀속 불가 명시 |

추가 보완: 정답 키 2벌을 `final-1`로 동결(사람 확정 표기), r3-K2는 다음 측정에서 양 조건
모두 포함으로 명시.

**판정 상태**: Codex의 조건부 결론을 따른다 — "finding-level 감사 기록, 실행 가능한
matcher와 결정성 검사, 정확한 provenance, 계약 rubric 분리를 갖추면 evidence-only
finding-key scorer를 측정 기반으로 수용". 앞의 두 조건은 위와 같이 충족했고, 남은 두 조건
(provenance 스탬프, runner의 diffContractRubric 분리)은 **재측정 전 구현 과제**다.

## 다음 단계 — 라운드 2 합의 반영

최종 hardened 0.15.0 vs 0.14.0 재측정의 전제 조건과 설계 (Codex 수정 제안 수용):

- **provenance 스탬프(확장)**: commit·dirty 여부에 더해, 실행에 실제 복사된 플러그인
  content manifest hash, runner·scorer·task·fixture·answer-key 각각의 버전/해시,
  CLI·모델·effort·실행 명령을 run record에 기록. 가능하면 실행 스냅샷 보관.
- **diffContractRubric 분리 (필수)**: 계약 유효성은 독립 hard gate로만 두고
  coverage·FP·근거 적합성에 합산하지 않는다.
- **지표 4축 분리 보고**: ① required-key coverage (macro·micro 병기, 주지표 사전 고정)
  ② finding 단위 FP (합계·run당·발생 run 비율) ③ 근거 적합성 ④ contract-valid /
  scorable 비율. "precision"은 finding별 TP/FP 저장 후에만 사용.
- **r3-K2 복원 — 양 조건 공통 적용**: 0.14.0에 해당 지식이 없었다는 것은 제외 사유가
  아니라 지식 snapshot 효과의 일부다. 단 "사실 발견 / diff 증거 제시 / 지식 근거 적합"을
  분리 채점한다.
- **반복 수 사전 규칙**: pilot으로 coverage·FP 분산 추정 → 최소 의미 차이와 허용
  불확실성 사전 정의 → confirmatory 반복 수 고정. pilot을 본실험에 포함하면 사전 정의된
  순차 정지 규칙 사용, 예산 내 판별력 부족 시 `판정 불가`로 종료.
