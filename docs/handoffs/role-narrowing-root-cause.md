# 역할 축소 사고 원인과 차단 — `06-r3-B-rep2`

발견: 2026-08-24 재측정 (`benchmarks/akasha-version-ab-2026-08-24/`)
수정: SKILL.md 2곳, `validateAkashaReview` 1곳, 회귀 테스트 6개

## 증상

r3 과업은 5개 역할(backend·data·platform·qa·security)이 필요하다. `06-r3-B-rep2`는
**qa 하나만 실행하고 종료했다.** 그 결과 정답 8항목 중 4항목만 커버했다(다른 런은 6~7항목).

문제는 결과가 아니라 **이 실행이 정상으로 기록됐다는 것**이다.

| 신호 | 값 |
| --- | --- |
| exit code | 0 |
| timed out | false |
| 형식 계약 유효 | **true** |
| JSON 파싱 오류 | 없음 |
| stderr 오류 | CLI 잡음뿐 (12런 중 10런에 등장, 정상 실행에도 있음) |

즉 할 일의 20%만 하고 **모든 검사를 통과했다.** 사람이 커버리지 표를 눈으로 보고 이상하다고
느낀 뒤에야 발견됐다.

## 부모가 실제로 한 말

```json
{ "role": "platform/security/data/backend",
  "spawned": false,
  "reason": "해당 승인 KB 및 역할 정의가 설치 범위에서 확인되지 않음",
  "risk_signals": ["CI permissions", "external input trust boundary", "data integrity"] }
```
```json
"fallbacks": [{ "reason": "역할 정의 파일 부재", "effect": "QA 서브에이전트 1개만 실행" }]
```

**역할 정의 파일은 있었다.** 같은 fixture에서 다른 4런은 5개 역할을 모두 찾았고, 이 런조차
qa 문서는 찾아 읽었다. 경로 해석이 깨졌다면 qa도 실패했어야 한다. 즉 **확인하지 않고 부재를
단정했다.**

## 왜 통과했나 — 빈틈 4개

### (a) 존재 확인이 "주장"으로 충분했다
SKILL.md는 지식 경로에 대해서는 "플러그인 루트 아래 실제 파일로 해석되는지 확인한 뒤에만
spawn한다"고 요구했지만, **역할 문서 자체에는 같은 요구가 없었다.** 부모는 읽어보지 않고
"확인되지 않음"이라고 쓸 수 있었다.

### (b) 파일 부재 시 행동 규정이 아예 없었다
문서에는 인접한 다른 규정만 있었다 — "`akasha-<역할>`을 **사용할 수 없는 환경**이면 일반
서브에이전트로 호출하되 역할 문서 절대 경로를 packet에 포함한다"(런타임 미지원 대응).
이 규정은 역할 수를 줄이라는 말이 전혀 아닌데, 부모는 규정이 없는 상황에서 이것을 유추 적용해
**역할 4개를 버리는 근거로 썼다.**

### (c) 기존 검사 규정이 우회 가능했다
"선택한 역할마다 성공한 호출이 정확히 하나 있는지 확인한다"는 규정은 이미 있었다. 그런데
부모는 4개 역할을 `spawned: false`로 처리했으므로 **자기 기준으로는 "선택한 역할"이 아니게
됐다.** 선택을 취소하면 검사 대상에서 빠지는 구조였다.

### (d) 계약 검증기가 `model_routes`의 내용을 보지 않았다
`validateAkashaReview`는 `model_routes`가 배열인지만 확인했다. 그래서 4개 역할을
`"platform/security/data/backend"` 한 문자열로 묶고 실행하지 않은 응답이 **형식상 완전히
유효했다.**

## 어떻게 막았나

### SKILL.md — (a), (b)
> 역할 후보는 위 세 절을 **실제로 읽어낸** 역할만이다. 따라서 신호로 고른 뒤에 "역할 정의를
> 찾지 못했다"는 이유로 그 역할을 취소하는 일은 성립하지 않는다 — 고를 수 있었다면 파일을
> 읽은 것이다. 읽기로 확인하지 않은 채 파일 부재를 단정하지 않는다.

존재 확인을 별도 단계로 추가하지 않았다. 팀 구성 단계에서 이미 각 역할 문서의 세 절을 읽으므로,
**읽어낸 역할만 후보가 된다는 사실을 명시하면 "파일이 없어서 취소" 상태가 구조적으로 발생할 수
없다.** 규칙을 늘리는 대신 이미 있는 동작의 논리적 귀결을 못 박았다.

### SKILL.md — (c)
> 신호로 고른 역할 수와 실제로 spawn한 수가 다르면 **그 실행은 실패다**. 남은 역할을 빼고
> 종합해 정상 응답으로 반환하지 않는다. spawn 호출 자체가 실패한 경우에만 역할 누락 보고를
> 따르며, **역할 정의 파일 부재는 누락 사유가 될 수 없다.**
>
> `model_routes`의 한 항목은 정확히 한 역할만 가리킨다. 위험 신호를 적은 역할은 반드시
> 실행한다. 위험을 인정하고 실행하지 않는 항목은 계약 위반이다.

### 검증기 — (d), 그리고 이게 핵심이다
(c)의 교훈은 **프롬프트 규정만으로는 또 샌다는 것**이다. "성공한 호출이 하나 있는지 확인한다"는
규정은 이미 있었는데도 우회됐다. 그래서 기계 검사를 추가했다
(`scripts/model-routing-lib.mjs`, `CONTRACT_VALIDATOR_VERSION` → `akasha-contract-2`).

- `model_routes[].role`은 비어 있지 않은 문자열이어야 하고 `/`나 `,`를 포함할 수 없다.
  여러 역할을 한 항목으로 묶는 우회를 막는다.
- `spawned: false`인 항목이 비어 있지 않은 `risk_signals`를 가지면 계약 위반이다.
  **위험을 인정하면서 실행하지 않는 것**이 이 사고의 기계적 서명이다.
- `risk_signals`가 빈 배열인 `spawned: false`는 허용한다. spawn 호출 자체가 실패한 정당한
  역할 누락 보고를 막지 않기 위해서다.

## 남은 한계

- **발생률은 여전히 모른다.** 10런 중 1런에서 관측됐다. 프롬프트 수정이 발생률을 얼마나
  낮추는지는 재측정해야 안다. 검증기는 발생을 막지 못하고 **조용히 통과하는 것만 막는다.**
- 검증기는 부모 응답 텍스트만 본다. 실제 자식 실행 수와 대조하는 것은 runner의
  `exact_roles`가 하고 있으며, 두 신호가 어긋나는 경우(예: 응답에는 5역할을 적고 실제로는
  1개만 실행)는 여전히 runner 쪽에서만 잡힌다. 프로덕션에는 그 대조가 없다.
- 이번 수정으로 계약 검증이 더 엄격해졌으므로, 다음 재측정의 `contract-valid` 수치는
  이전 8/10과 정의가 다르다. `CONTRACT_VALIDATOR_VERSION`으로 구분한다.
